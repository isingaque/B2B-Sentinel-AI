# Sentinel AI — инженерный отчёт ML v1.6

**Статус:** исследовательская ветка `classifier-fullcontext-v16`. Стабильная `main` сохранена, автоматического слияния нет. Модель не использует внешние LLM или платные API.

## 1. Что сделано как ML-инженерная работа

- Проверена воспроизводимость существующего baseline (экспертный классификатор v1.1, экспертный v2 и обученный TF-IDF/SVM v1.4).
- Исправлена важная часть бизнес-логики: приоритет — **не просто копия критичности**, он зависит от окружения (production или non-production), как предписывает техническое ТЗ.
- Собраны **745 определений реальных опубликованных Prometheus alert rules** из 71 файлового источника, с фиксацией `source_file` и точного Git SHA.
- Для всех 745 правил сохранены название, `summary`, `description`, выражение PromQL и настроенная критичность. Категория — приближённая редакторская разметка по семейству экспортёра.
- Построены два обученных классификатора TF-IDF (символьные и словные n-граммы) + линейный SVM: **production_text** для реально доступных `alertname+summary+description`, **promql_research** для контекста с выражениями PromQL, требующего дополнительной интеграции.
- Реализованы контроль разделения по экспортёрам, измерение per-label accuracy, macro-F1, совместной точности, confusion matrices и перечней ошибок.
- Обучение включено в сборку экспериментального Docker-образа; **готовые ответы категории и severity не передаются обученной модели при проверке**.

Первоисточник конфигураций: [samber/awesome-prometheus-alerts](https://github.com/samber/awesome-prometheus-alerts). Это настоящие опубликованные правила, но **не журнал реальных произошедших аварий**. Отчёт не утверждает, что данные являются production incidents.

## 2. Строгая проверка переноса по семействам экспортёров

До обучения модели с описаниями проведена 5-fold GroupKFold-проверка **по 745 публичным правилам из 66 семейств экспортёров**. В каждом фолде целые семейства находятся либо в обучении, либо в тесте; совпадающие названия исключаются из обучения. Настройка SVM взята из предшествующего эксперимента, поэтому эти числа **разведочные**, а не новая независимая финальная оценка.

| Метод (только название предупреждения) | Category accuracy | Severity accuracy | Совместно | Category macro-F1 | Severity macro-F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| v1.1, экспертные правила | 47,8% | 31,5% | 14,9% | 39,4% | 31,4% |
| v2, расширенные экспертные правила | **76,2%** | 66,7% | **51,7%** | **75,0%** | 50,5% |
| v1.4, обученная SVM | 51,5% | **67,2%** | 34,9% | 41,6% | **53,8%** |
| Гибрид v2 + SVM | 76,2% | 67,2% | 50,7% | 75,0% | 53,8% |

Количество примеров по классам: application — 288, database — 234, server — 137, network — 86. Это существенно лучше по представительности категорий, чем один тест на 118 примерах.

## 3. Обучение с реальными аннотациями Prometheus

Фиксированные выборки и гиперпараметры:

| Набор | Объём | Применение |
| --- | ---: | --- |
| Train | 553 | Обучение весов моделей |
| Validation | 74 | Выбор регуляризации, без финальных примеров |
| Holdout | 118 | Разовая финальная проверка на других экспортёрах |

Три выборки не пересекаются по семействам экспортёров; тренировочный скрипт **не читает финальную выборку**. Вход рабочей модели: название, summary и description; исходный `severity` и категория в векторизатор не попадают. Для модели с PromQL дополнительно подаётся выражение, доступное в опубликованной конфигурации, но не в обычном ответе `/api/v1/alerts`.

**Валидация (74 опубликованных правила):**

| Метод | Категория | Критичность | Совместно |
| --- | ---: | ---: | ---: |
| v1.1 с описаниями | 56,8% | 43,2% | 23,0% (17/74) |
| v2 с описаниями | 70,3% | 66,2% | 48,6% (36/74) |
| **Обученная v1.6 по доступным аннотациям** | 64,9% | 71,6% | 47,3% (35/74) |
| Обученная v1.6 + PromQL, исследовательский режим | 74,3% | 74,3% | 58,1% (43/74) |

Для рабочей модели `production_text` выбран `C=1.0`, для отдельного исследования `promql_research` — `C=4.0`. Выбор сделан до итоговой проверки.

**Итоговый holdout (118 правил новых семейств):**

| Метод | Категория | Критичность | Совместно |
| --- | ---: | ---: | ---: |
| v1.1 с описаниями | 51,7% | 37,3% | 17,8% (21/118) |
| v2 с описаниями | 44,1% | 68,6% | 28,0% (33/118) |
| **Обученная v1.6 по доступным аннотациям** | **67,8%** | **80,5%** | **55,1% (65/118)** |
| v1.6 + PromQL, исследовательский режим | 71,2% | 80,5% | 55,1% (65/118) |

Достижение 90% не подтверждено. Добавление описаний помогло, но данных, позволяющих независимо предсказать все три признака с таким качеством, пока недостаточно. Контрольный набор из 118 правил содержит только **5 network-примеров** — он не соответствует целевой балансировке из внутреннего ТЗ (минимум 20 примеров на категорию), поэтому нельзя использовать его одного как окончательную приёмку.

### Почему результат ML отличается от обработки нормализованных меток

В стандартном ответе Prometheus `labels.severity` может уже содержать установленное в мониторинге значение `critical`/`warning`/`info`. Использование этого значения даёт правильную нормализацию и расчёт приоритета, **но не самостоятельное предсказание ML-модели**. Эти два сценария всегда необходимо показывать жюри отдельно.

## 4. Приоритет по техническому ТЗ

В `backend/app/priority_policy.py` реализована доменная политика:

| Severity | Production | Non-production |
| --- | --- | --- |
| critical | P1 | P2 |
| warning | P2 | P3 |
| info | P4 | P4 |

Если `environment`/`env` отсутствует либо противоречив, система консервативно считает окружение production и требует проверки инженером. Политика применяется в сервисном слое ко всем экспериментальным классификаторам, независимо от способа классификации; сохраняется статус ручной проверки. Спецификация исходно предусматривала разделение severity и priority — это реальная функциональная доработка.

## 5. Запуск без платных API

Скачайте ZIP экспериментальной ветки `classifier-fullcontext-v16` в отдельную папку, не заменяя v1.1. В PowerShell из корня новой папки:

```powershell
Copy-Item .env.example .env
```

В файле `.env` выставьте:

```dotenv
CLASSIFIER_ENGINE=context
FRONTEND_PORT=8084
PROMETHEUS_PORT=9094
```

Запуск из новой папки:

```powershell
docker compose -p sentinel_ai_context_v16 up --build -d
docker compose -p sentinel_ai_context_v16 ps
```

UI: http://localhost:8084 . Обе модели обучаются в Docker build, без сторонних API. Ветка поддерживает обратное переключение на `CLASSIFIER_ENGINE=v2` или `legacy`.

**Ограничение:** Docker Smoke Test на компьютере команды ещё не проводился; GitHub Actions проверяет Python-код, данные и сборку Frontend, но не заменяет полноценное интеграционное испытание.

## 6. Воспроизведение тестов и артефакты

После установки `backend/requirements-dev.txt`:

```bash
cd backend
python -m app.ml_v14 --train
python -m app.ml_v16 --train
PYTHONPATH=. python ../scripts/evaluate_groupcv_v15.py --json-out ../reports/groupcv_v15.json
PYTHONPATH=. python ../scripts/evaluate_context_v16.py --final --json-out ../reports/annotation_v16_holdout.json
pytest -q
```

В GitHub Actions сохраняются JSON-отчёты с матрицами ошибок и перечнями промахов как артефакт `sentinel-ai-ml-evaluation`, который можно скачать и предъявить жюри вместе с исходниками и воспроизводимыми командами.
