# Проверка классификации и поиска регламентов — экспериментальная ветка

Этот документ описывает **реальные результаты проведённых проверок**, а не обязательную достигнутую точность.

## 1. Проверка на внешних опубликованных правилах Prometheus

**Источник:** открытый репозиторий [samber/awesome-prometheus-alerts](https://github.com/samber/awesome-prometheus-alerts), файлы из `dist/rules/`. Фикстура: [public_prometheus_rules.csv](../backend/tests/fixtures/public_prometheus_rules.csv). В каждой строке указаны `source_file` и `source_sha` для проверки происхождения.

Собрано **185 определений alert rules**, относящихся к 14 конфигурациям:
- server — 48 правил: node exporter и systemd;
- network — 51 правило: blackbox, SNMP, Cilium и Juniper;
- database — 59 правил: PostgreSQL, MySQL и Redis;
- application — 27 правил: Nginx, Apache, PHP-FPM, Go, Python.

**Как формировались эталонные значения:**
- `alert_name` и `severity` взяты из внешних, опубликованных Prometheus-конфигураций;
- `category` определена по семейству экспортера (например, PostgreSQL → database). Это **приближённая разметка по коллекции**, а не экспертная оценка каждого реального случая;
- `priority` является производным значением (`critical→P1`, `warning→P2`, `info→P4`), а не отдельной независимой разметкой;
- фикстура не содержит полных описаний событий, временных рядов, порогов и информации о реальном сбое.

**Что получает классификатор:** только `alert_name`. Поля `category`, `severity`, исходные каталоги, `source_sha` и другие эталонные подсказки **не передаются**. Это намеренно более жёсткий тест, чем стандартная работа с полноценным событием Prometheus.

### Результаты стандартного rule-based классификатора v1.1

| Метрика | Точность |
| --- | ---: |
| Category | 47,6% |
| Severity | 33,5% |
| Priority (выведен из severity) | 33,5% |
| Совместная точность category + severity + priority | **17,8% (33/185)** |

Ошибки: 152 из 185. Измерения воспроизводимы в GitHub Actions и в локальном окружении. Полные матрицы ошибок и список несовпадений могут быть записаны в JSON.

**Интерпретация:** в режиме `alert_name`-only нельзя утверждать, что требование ≥90% выполнено. Часть предупреждений с похожими названиями имеет разную критичность в зависимости от порогов PromQL, поэтому только по названию верно восстановить severity невозможно. В реальной системе используются описание и метки Prometheus; результаты для них могут существенно отличаться. Данный бенчмарк — **внешние правила мониторинга, не реальные произошедшие инциденты**.

## 2. Проверка подбора регламентов

[Скрипт](../scripts/evaluate_retrieval.py) проверяет пять первоначальных регламентов Sentinel AI на 15 вручную составленных русско- и англоязычных формулировках, в том числе перефразированных.

При стандартном `EMBEDDING_BACKEND=hash`:

| Метрика | Результат |
| --- | ---: |
| Top-1 | 15/15 (100%) |
| Top-3 recall | 15/15 (100%) |

Эта проверка **не доказывает общее качество семантического поиска**: всего пять регламентов, сравнительно небольшой тест и заранее заданная категория события. Она лишь позволяет воспроизвести поведение текущего ранжирования на известных сценариях.

Для настоящих нейросетевых эмбеддингов в v1.1 есть необязательная модель `intfloat/multilingual-e5-small`. Она не включается автоматически. Описание режима и миграции векторов: [EXPERIMENTAL_E5.md](EXPERIMENTAL_E5.md). Измерение E5 на тестовой машине требует скачивания модели. **Результат для E5 в этом отчёте не заявляется**, так как эта проверка ещё не выполнена.

## 3. Как воспроизвести проверки

С компьютера с установленными зависимостями Python:

```bash
cd backend
pytest -q
PYTHONPATH=. python ../scripts/evaluate_public_rules.py --json-out ../reports/public_rules.json
PYTHONPATH=. python ../scripts/evaluate_retrieval.py --backend hash --json-out ../reports/retrieval_hash.json
```

Через работающий Docker Compose, без локального Python, из корня проекта в Windows PowerShell:

```powershell
docker compose cp .\backend\tests api:/srv/tests
docker compose cp .\scripts\evaluate_public_rules.py api:/srv/evaluate_public_rules.py
docker compose cp .\scripts\evaluate_retrieval.py api:/srv/evaluate_retrieval.py

docker compose exec api python /srv/evaluate_public_rules.py --dataset /srv/tests/fixtures/public_prometheus_rules.csv
docker compose exec api python /srv/evaluate_retrieval.py --backend hash
```

Оба скрипта **не изменяют базу данных** и не создают инциденты. Для воспроизведения E5 сначала настройте и установите опциональные зависимости модели в отдельном тестовом окружении. Переключение на E5 в текущем Docker-томе требует пересчёта эмбеддингов: смешивать hash и E5 нельзя.

## 4. Что нужно для строгой приёмки ≥90%

Для формального подтверждения потребуется:
1. Получить новые, неиспользованные при доработке инциденты с полями, реально доступными системе (alert name, summary, description, labels).
2. Получить независимую экспертную разметку категории, критичности и приоритета для каждого инцидента.
3. Заморозить набор до изменения модели или правил, исключить случаи утечки эталонных меток, заранее утвердить критерий качества.
4. Оценить category, severity, priority, joint exact match, confusion matrix, а также качество поиска регламентов (top-k/recall) на отдельном наборе.
5. Только после получения результата не ниже 90% **на этом независимом тесте** заявлять о соответствии требованию.

**Примечание:** использование самих `severity` или `category` от Prometheus может быть полезной нормализацией источника, но не является независимым предсказанием этих полей. Это нужно учитывать при интерпретации метрик.

## 5. Изоляция от стабильного приложения

Ветка `quality-validation-v11` добавляет тестовые данные, оценочные скрипты, тесты и документацию. **Бизнес-логика v1.1 и стандартный AI-классификатор не изменены; GitHub `main` не изменена**. Это безопасная первая стадия объективной оценки перед отдельной доработкой алгоритма.
