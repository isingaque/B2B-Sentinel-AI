# Sentinel AI v1.2 (offline) — классификация и проверка качества

Статус: **экспериментальная ветка** `classifier-v12-offline`. 
Стабильная версия v1.1 в `main` не меняется.

## 1. Что реализовано

Добавлен модуль [`backend/app/triage_v2.py`](../backend/app/triage_v2.py).

Новый классификатор работает локально и не требует DeepSeek, OpenRouter, платных API, GPU или загрузки языковой модели. Алгоритм использует:
- структуру имён предупреждений Prometheus (включая CamelCase);
- семейство мониторинга, технические признаки и текст описания;
- допустимые категории `server`, `network`, `database`, `application`;
- значения `severity` и `category`, **если их предоставил сам источник мониторинга**;
- признаки критичного отказа, деградации и информационных событий;
- расчёт приоритета сервером: `critical → P1`, `warning → P2`, `info → P4`.

Результат сохраняется в существующей модели `Analysis`, включая объяснение и `model_version=offline-triage-v2`. Структура БД не менялась; алгоритм подбора регламентов и ручной порядок выполнения чек-листов сохранены.

**Принципиальное ограничение:** v2 — объяснимая экспертная система, **не обученная нейронная сеть**. Её выводы не имеют статистически откалиброванной вероятности. Поэтому `confidence=null`, `review_required=true`, а интерфейс показывает «Требует проверки» без выдуманного процента.

При `CLASSIFIER_ENGINE=legacy` сохраняется прежний алгоритм из v1.1.

## 2. Источник данных для оценки

Оба набора заморожены в Git и составлены из опубликованных определений предупреждений проекта [awesome-prometheus-alerts](https://github.com/samber/awesome-prometheus-alerts). Для каждого примера сохранены имя правила, severity, путь к исходному файлу и SHA исходного содержимого.

Категория размечена **по семейству экспортера**, поэтому иногда является приближённой. Критичность взята из метки `severity` исходного правила, но **не передаётся на вход классификатору**. В бенчмарке доступно только название alert, **без описания, порогов PromQL и меток источника**.

Эти объекты — **опубликованные правила мониторинга, а не реальные произошедшие производственные инциденты**.

- Разработческий набор: [185 правил, 14 конфигураций](../backend/tests/fixtures/public_prometheus_rules.csv). Этот набор изучался при проектировании v2.
- Отложенный набор: [158 правил, 13 других конфигураций](../backend/tests/fixtures/heldout_prometheus_rules.csv). Эти семейства экспортёров не использовались для первоначальной настройки v2. Это более строгая проверка переноса на новые источники, но не подтверждённый промышленный набор.

## 3. Результаты оценки

**Разработческий набор (185 правил):**

| Метрика | v1.1 (legacy) | v1.2 (offline v2) |
| --- | ---: | ---: |
| Категория | 47,6% | 100,0% |
| Критичность | 33,5% | 73,5% |
| Приоритет | 33,5% | 73,5% |
| Совместно три признака | **17,8% (33/185)** | **73,5% (136/185)** |

Разработческий набор **не является независимой оценкой после подбора алгоритма**.

**Отложенный набор (158 правил других экспортёров):**

| Метрика | v1.1 (legacy) | v1.2 (offline v2) |
| --- | ---: | ---: |
| Категория | 27,9% | 77,2% |
| Критичность | 31,0% | 60,8% |
| Приоритет | 31,0% | 60,8% |
| Совместно три признака | **9,5% (15/158)** | **46,8% (74/158)** |

Точность на новом наборе существенно выросла, но порог ≥90% **не достигнут**.

**Два прежних собственных синтетических набора:**

| Набор | v1.1 | v1.2 |
| --- | ---: | ---: |
| 24 вручную составленных события | 91,7% | 100% |
| 48 вручную составленных события | 95,8% | 100% |

Эти 72 случая использовались для разработки и регрессионных проверок, поэтому **их нельзя выдавать за независимую валидацию**.

Все показатели являются точностью определения категории, критичности и приоритета **одновременно**. Поскольку приоритет определяется критичностью, эти признаки статистически связаны. Метрика для `priority` не измеряет отдельно обученную классификацию приоритетов.

## 4. Почему 90% пока не доказано

Имя правила часто не содержит порога или контекста, который определяет критичность. Одно и то же название проблемы может иметь `warning` у одного владельца инфраструктуры и `critical` у другого.

В обычном режиме Sentinel AI получает от Prometheus также `labels` и `annotations`. Если источник передал `severity`, система правильно использует её для расчёта приоритета. **Это надёжная обработка данных источника, но не независимое предсказание критичности.**

Чтобы доказать требование ≥90%, нужен согласованный с организатором независимый набор полноценного формата, с экспертной разметкой категорий, критичности и приоритета. Для проверки такого набора реализован [`evaluate_labeled_incidents.py`](../scripts/evaluate_labeled_incidents.py).

## 6. Безопасный запуск отдельно от v1.1

Для демонстрации стабильной версии используйте `main`. Чтобы протестировать v2, скачайте ZIP ветки `classifier-v12-offline` и распакуйте в **отдельную папку**, не заменяя работающую v1.1.

В PowerShell из новой папки:

```powershell
Copy-Item .env.example .env
```

Убедитесь, что в `.env` установлены:

```dotenv
CLASSIFIER_ENGINE=v2
FRONTEND_PORT=8082
PROMETHEUS_PORT=9092
```

Запустите отдельный Compose-проект:

```powershell
docker compose -p sentinel_ai_offline_v12 up --build -d
docker compose -p sentinel_ai_offline_v12 ps
```

Адрес экспериментального интерфейса: http://localhost:8082 . 
Использование отдельного имени проекта и портов создаёт **отдельные Docker-тома и отдельную БД**, не удаляя историю из v1.1.

Для возврата к прежнему классификатору измените `CLASSIFIER_ENGINE=legacy` и пересоздайте `api` и `worker`:

```powershell
docker compose -p sentinel_ai_offline_v12 up -d --force-recreate api worker
```

Для полного отчёта на GitHub доступны результаты [GitHub Actions](https://github.com/isingaque/B2B-Sentinel-AI/actions). Непосредственный Docker Smoke Test экспериментальной версии на компьютере пользователя необходимо выполнить отдельно до использования на защите.

## 7. Как воспроизвести внешние оценки без локального Python

После запуска Docker, из корня ветки `classifier-v12-offline`:

```powershell
docker compose -p sentinel_ai_offline_v12 cp .\backend\tests api:/srv/tests
docker compose -p sentinel_ai_offline_v12 cp .\scripts\evaluate_public_rules.py api:/srv/evaluate_public_rules.py

docker compose -p sentinel_ai_offline_v12 exec api python /srv/evaluate_public_rules.py --engine v2 --dataset /srv/tests/fixtures/public_prometheus_rules.csv

docker compose -p sentinel_ai_offline_v12 exec api python /srv/evaluate_public_rules.py --engine v2 --dataset /srv/tests/fixtures/heldout_prometheus_rules.csv
```

Оценочные скрипты не изменяют данные PostgreSQL. Новые файлы и расчёты не требуют внешних AI API.
