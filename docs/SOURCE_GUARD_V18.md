# Sentinel AI v1.8 — разногласия ML и Prometheus: источник vs прогноз

Экспериментальная ветка: `ml-source-guard-v18`. Стабильная версия в `main` **не изменена**.

## Почему произошло расхождение в сценарии «Высокая загрузка CPU»

В настоящем файле конфигурации демо-приложения [`prometheus/alerts.yml`](../prometheus/alerts.yml) правило `HighCPUUsage` уже содержит:

```yaml
labels:
  severity: critical
  category: server
annotations:
  summary: "Высокая загрузка CPU на сервере"
  description: "CPU utilization exceeded 95% for server node-01; inspect processes and load."
```

В приложении старые правила v1.1 на текстовом сравнении дали `server / critical`, а обученная TF-IDF + SVM v1.6 — `server / warning`. Это **расхождение прогнозов**.

Демо-сигнал активируется не измерением настоящего CPU, а переключателем `demo_incident_active{scenario="cpu_high"}` в [`exporter/app.py`](../exporter/app.py). Правило `HighCPUUsage` в [`prometheus/alerts.yml`](../prometheus/alerts.yml) реагирует на `demo_incident_active == 1`; описание про 95% — заранее заданный текст, **а не измеренный процент на хосте**.

Следовательно, мы можем проверить совпадение с *настройками мониторинга*, но не объявить по этому сценарию, что SVM ошиблась на реальных технических метриках.

## Улучшение логики в v1.8

Добавлен опциональный режим `CLASSIFIER_ENGINE=context_guarded`. Он делает оба шага:

1. Модель v1.6 предсказывает `category` и `severity` **только по тексту** (`alert_name`, `summary`, `description`); категория/критичность из Prometheus не подмешиваются в признаки.
2. Для *операционного решения* известные метки `labels.category` и `labels.severity` Prometheus приоритетнее ML-прогноза. Если меток нет или они не распознаны, используется прогноз ML. Если источник и модель расходятся, объяснение предупреждает об этом и требует проверки инженером. Значение приоритета рассчитывается по severity + окружению (production / non-production).

Модель не переобучается на демо-сценарии, класс `warning` не «исправляется» искусственно. Изменена политика принятия решения, **не измеренная точность независимой ML-классификации**.

Новый [`backend/app/source_guard.py`](../backend/app/source_guard.py) возвращает также первоначальный ML-прогноз и эталонные метки источника. В активном анализе объяснение фиксируется в БД, а в сравнении выводится отдельный блок «Что применять в работе».

### Для сценария CPU из симулятора

| Источник ответа | Категория | Критичность |
| --- | --- | --- |
| Прогноз v1.1 только по тексту | server | critical |
| Прогноз ML v1.6 только по тексту | server | warning |
| Метки правила Prometheus | server | critical |
| Решение `context_guarded` | server | **critical** |

При неизвестном окружении приоритет рассчитывается как **P1 (консервативный production)** и требуется ручная проверка. Для staging будет P2, согласно бизнес-политике. Если в реальном событии нет допустимой `severity`, система **не придумывает метку источника** и берёт ML-прогноз с ручной проверкой.

## Как запустить

Скачай ZIP этой ветки, распакуй **в отдельную папку**, открой PowerShell там, где лежит `docker-compose.yml`:

```powershell
Copy-Item .env.example .env
notepad .env
```

Укажи в `.env`:

```dotenv
CLASSIFIER_ENGINE=context_guarded
FRONTEND_PORT=8086
PROMETHEUS_PORT=9096
```

```powershell
docker compose -p sentinel_ai_guard_v18 up --build -d
docker compose -p sentinel_ai_guard_v18 ps
```

Интерфейс: **http://localhost:8086**.

В симуляторе включи «Высокая загрузка CPU», затем открой инцидент → «ИИ-анализ» → «Сравнить v1.1 и ML v1.6». Новые анализы в этом режиме будут хранить рабочую critical/P1 по источнику, одновременно в отдельной сравнительной панели будет видно, что ML сама предсказала warning.

Сравнение — **GET без изменений** основной записи. Для ранее созданного инцидента переключение `CLASSIFIER_ENGINE` не изменит исторический ответ: можно запросить новый анализ кнопкой «Пересчитать», если инцидент не закрыт. При смене настройки также пересоздай `api` и `worker`:

```powershell
docker compose -p sentinel_ai_guard_v18 up -d --force-recreate api worker
```

Остановить только эту экспериментальную версию:

```powershell
docker compose -p sentinel_ai_guard_v18 down
```

**Не используй `down -v`**, если хочешь сохранить данные.

## Что можно утверждать на защите

«В системе есть независимый ML-прогноз, который мы сравниваем с правилом экспертов и метаданными мониторинга. При расхождении источник мониторинга приоритетен в рабочем решении, а ML-прогноз сохраняется для анализа ошибок; инженер проверяет исходные метрики. Демо-сценарий с CPU активируется искусственным переключателем, поэтому он проверяет обработку сигналов, а не точность диагностики реального сервера».

Внешняя проверка v1.6 по 118 опубликованным правилам дала 55,1% совместной точности категории и severity (с ограничениями датасета). Эта цифра **не меняется**, потому что v1.8 не обучает новую модель и не создаёт новый независимый тест.

Гарантировать точность ≥90% на реальных инцидентах по этому демо нельзя.
