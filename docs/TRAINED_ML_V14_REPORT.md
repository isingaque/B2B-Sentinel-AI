# Sentinel AI: локальное обучение классификатора, эксперимент v1.4

**Статус:** экспериментальная ветка `classifier-ml-v14`. Стабильная `main` не изменена. **Требование ≥90% на независимо размеченных реальных инцидентах пока не подтверждено.**

## Что реализовано

Обучаемая модель [`backend/app/ml_v14.py`](../backend/app/ml_v14.py): TF-IDF по символьным n-граммам и словам, линейный SVM (`scikit-learn`). Обучается **локально во время Docker build** из зафиксированных CSV, не использует внешние LLM, платные API и не изменяет БД. Модель предсказывает категорию и критичность. Приоритет `P1/P2/P4` получается из предсказанной или полученной от источника критичности.

Старая классификация сохранена. `confidence=null` и `review_required=true`: оценка SVM без калибровки не является достоверной вероятностью и не показывается как процент уверенности. Выполнение действий по-прежнему только ручное, после проверки инженером.

## Данные и условия исследования

Источник: [samber/awesome-prometheus-alerts](https://github.com/samber/awesome-prometheus-alerts), опубликованные определения Prometheus alert rules. Исходные тексты правил распространяются под [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Для эксперимента извлечены названия предупреждений и настройки `severity`, присвоена категория по семейству экспортёра. Исходные файлы и SHA опубликованы в каждом CSV.

**Это не журнал реально случившихся производственных инцидентов.** Категории являются прокси-разметкой по типу экспортёра (не индивидуальной экспертной разметкой). Критичность — значение из внешней конфигурации. В обучении и оценке по названиям критичность и категория **не передаются модели как входные метки**.

Зафиксировано три раздельных набора по *семействам экспортёров*, а не случайным строкам:

| Набор | Примеры | Назначение |
| --- | ---: | --- |
| Обучение | **553** | Подгонка весов TF-IDF + SVM |
| Валидация | **74** | Выбор коэффициента регуляризации и гибридной стратегии |
| Итоговая проверка | **118** | Другие семейства экспортёров, не участвовавшие в обучении и выборе стратегии |

В обучении участвуют ранее собранные коллекции 185 и 158 правил (они больше **не считаются независимым тестом** в v1.4) и два дополнительных CSV. Третий новый CSV предназначен для валидации, последние два — для финальной проверки.

Обучающий скрипт **не открывает и не читает** финальные два CSV. При оценке из финального набора исключаются точные совпадения названий с обучением, а одинаковые семейства экспортёров между тренировочным и тестовым набором запрещены. Фактически на финальной проверке исключено **0 совпадений**.

## Точные результаты, зафиксированные в GitHub Actions

**Валидация на 74 правилах:**

| Классификатор | Категория | Критичность | Вместе |
| --- | ---: | ---: | ---: |
| Старые правила v1.1 | 63,5% | 39,2% | 24,3% |
| Экспертные правила v2 | 70,3% | 58,1% | 41,9% |
| Чистая TF-IDF + SVM | 59,5% | 71,6% | 44,6% |
| Гибрид (правила для категории + SVM для критичности) | 70,3% | 71,6% | **55,4% (41/74)** |

Гибрид выбран **только по валидации**, без обращения к финальному набору.

**Финальная проверка на 118 правилах новых семейств:**

| Классификатор | Категория | Критичность | Вместе |
| --- | ---: | ---: | ---: |
| Старые правила v1.1 | 44,9% | 34,8% | 11,9% (14/118) |
| Экспертные правила v2 | 45,8% | 73,7% | 35,6% (42/118) |
| **Чистая TF-IDF + SVM** | **56,8%** | **80,5%** | **48,3% (57/118)** |
| Гибрид, выбранный по валидации | 45,8% | 80,5% | 35,6% (42/118) |

Самостоятельная ML-модель превзошла старую на финальных правилах, **но до 90% не приблизилась**. Гибрид на новых источниках не подтвердил выигрыш по совместной метрике, показав переориентацию на особенности валидационной группы.

Нельзя выбирать лучшую строку **по результату финального набора** и выдавать его за новый, по-прежнему независимый тест выбранной после оценки стратегии. Для новой настройки потребуется ещё один закрытый контрольный набор.

## Режимы классификации

Переключаются в локальном `.env`, с пересозданием `api`/`worker`:

- `CLASSIFIER_ENGINE=legacy`: прежняя v1.1.
- `CLASSIFIER_ENGINE=v2`: офлайн экспертные правила, значение по умолчанию.
- `CLASSIFIER_ENGINE=ml`: гибридная стратегия, **выбранная только на валидации**. Метки категории/критичности Prometheus используются как информация источника.
- `CLASSIFIER_ENGINE=learned`: чистая обученная модель для экспериментального сравнения. При оценке `learned` не передаются правильные метки.

Для обычной защиты **предпочтительна проверенная v1.1** в `main`. Экспериментальная ML-версия не рекомендуется как гарантированно более точная при реальных инцидентах.

## Как запустить на отдельном Docker Compose-проекте

Скачайте ZIP ветки `classifier-ml-v14` в отдельную папку (не заменяйте исходники `main`). В Windows PowerShell из новой папки:

```powershell
Copy-Item .env.example .env
```

В `.env`:

```dotenv
CLASSIFIER_ENGINE=learned
FRONTEND_PORT=8083
PROMETHEUS_PORT=9093
```

Для сборки и запуска:

```powershell
docker compose -p sentinel_ai_ml_v14 up --build -d
docker compose -p sentinel_ai_ml_v14 ps
```

Интерфейс: http://localhost:8083 .

Новая сборка установит `scikit-learn`, создаст веса модели внутри образа и запустит приложение. Отдельное имя Compose-проекта и порты не затрагивают Docker-тома и историю стабильного приложения.

Для переключения на гибридную стратегию замените `CLASSIFIER_ENGINE=ml` и примените:

```powershell
docker compose -p sentinel_ai_ml_v14 up -d --force-recreate api worker
```

Не используйте `docker compose down -v`: это удалит данные выбранного проекта.

## Воспроизведение и CI

После установки зависимостей в `backend`:

```bash
python -m app.ml_v14 --train
PYTHONPATH=. python ../scripts/evaluate_ml_v14.py
PYTHONPATH=. python ../scripts/evaluate_ml_v14.py --final
pytest -q
```

GitHub Actions выполняет обучение, обе оценки и сборку Frontend. В модели используются только локальные обучающие CSV, итоговая выборка доступна **только оценочному скрипту**. Не следует загружать недоверенные файлы `joblib`: в Python десериализация pickle/joblib может исполнять код.

Важное ограничение: CI **не выполняет полноценных Docker E2E или интеграционных испытаний Prometheus**. Перед живой демонстрацией версии v1.4 нужен отдельный Smoke Test на компьютере команды.

## Как добиться подтверждённых 90%

Потребуются реальные или полностью репрезентативные события со сведениями `alertname`, `summary`, `description`, `job`, конфигурацией порогов, временными рядами и экспертными категориями/критичностью. Необходимо заранее определить, допускается ли передавать модели `labels.severity`: при этом критичность уже известна из источника и не является самостоятельным AI-предсказанием.

Для честного независимого тестирования оставляют невиданный ранее набор событий, исключают целевые метки из входа и измеряют совместное совпадение категории, критичности и приоритета. Пока таких данных нет, **не утверждайте на защите, что точность 90% доказана**.
