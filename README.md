# Sentinel AI v1.8

**ИИ-ассистент дежурного инженера для обработки инфраструктурных инцидентов**  
Кейс № 8 хакатона ТПУ · Локальный MVP · [GitHub Actions](https://github.com/isingaque/B2B-Sentinel-AI/actions)

Sentinel AI получает предупреждения из **Prometheus**, регистрирует инциденты, анализирует их локальной обученной ML-моделью, сверяет результат с метками источника, рекомендует регламенты реагирования и помогает инженеру вести чек-листы и аудит.

**Основной режим v1.8 — `context_guarded`: ML-прогноз + проверка меток Prometheus + обязательное участие человека.** Сервис не выполняет команды на инфраструктуре, не перезапускает службы и не устраняет инциденты автоматически.

## Возможности

| Модуль | Реализация |

## Быстрый запуск

Нужны **Docker Desktop / Docker Engine с Compose v2**, доступ в интернет при первой сборке и свободные порты **8080** и **9090**. Python, Node.js, API-ключи и платные внешние LLM не требуются. Во время сборки Backend локально обучает модели из включённых в репозиторий CSV; первая сборка поэтому может занять больше времени.

**Windows PowerShell:**

```powershell
git clone https://github.com/isingaque/B2B-Sentinel-AI.git
cd B2B-Sentinel-AI
Copy-Item .env.example .env
docker compose up --build -d
docker compose ps
```

**Linux / macOS:**

```bash
git clone https://github.com/isingaque/B2B-Sentinel-AI.git
cd B2B-Sentinel-AI
cp .env.example .env
docker compose up --build -d
docker compose ps
```

После запуска:

| Сервис | URL |
| --- | --- |
| Веб-интерфейс | http://localhost:8080 |
| API / Swagger | http://localhost:8080/docs |
| Prometheus | http://localhost:9090 |
| Проверка Backend | http://localhost:8080/health/ready |

Демо-аккаунты: `admin` и `operator`; пароль для локального тестирования — `DemoPass123!`. Для любого публичного развёртывания **замените** `POSTGRES_PASSWORD`, `JWT_SECRET`, `DEMO_PASSWORD` и `DEMO_TOKEN` в `.env` и настройте TLS и ограничения доступа.

**Если у тебя остался `.env` от v1.1 или v1.2:** проверь, что там установлено `CLASSIFIER_ENGINE=context_guarded`. Значение из существующего `.env` не обновляется само при `git pull`. После изменения запускай `docker compose up --build -d` или пересоздай `api`, `worker`, `scheduler`. При переключении режима старые сохранённые анализы не изменяются автоматически — для нового результата используй кнопку «Пересчитать».

### Запуск рядом со старой версией

Чтобы не затронуть уже работающую установку v1.1, распакуй/клонируй v1.8 **в отдельную папку**, задай в новом `.env` другие порты:

```dotenv
CLASSIFIER_ENGINE=context_guarded
FRONTEND_PORT=8086
PROMETHEUS_PORT=9096
```

Затем из новой папки:

```powershell
docker compose -p sentinel_ai_guard_v18 up --build -d
```

Открывай http://localhost:8086. Отдельное имя Compose-проекта создаёт отдельные тома PostgreSQL и Redis. **Не используй `docker compose down -v`** для окружения с нужными данными.

## Как продемонстрировать v1.8

1. Войти в Sentinel AI как `admin`, открыть **«Симулятор»** и включить «Высокая загрузка CPU».
2. Дождаться появления предупреждения в Prometheus → Alerts и инцидента в Sentinel AI → **«Инциденты»**. В демо используется переключаемая метрика `demo_incident_active`: **фактическая загрузка CPU не создаётся и не измеряется**.
3. Открыть карточку: проверить рабочую категорию, критичность, приоритет, объяснение и состояние «Требует проверки».
4. Нажать **«Сравнить v1.1 и ML v1.6»**. Обе модели получают одинаковые `alertname`, `summary`, `description`, но не получают готовые метки категории/критичности.
5. Посмотреть **сверку с Prometheus**: правило `HighCPUUsage` задаёт `severity=critical`, а SVM может самостоятельно предсказать `warning`. В основном режиме v1.8 для реагирования используется значение мониторинга с предупреждением о расхождении.
6. Перейти к рекомендованному регламенту, принять план, вручную пройти чек-лист.
7. В **«Симуляторе»** нажать **«Сбросить все сигналы»**. После опросов Prometheus тревоги должны стать `INACTIVE`; правила останутся в списке Alerts, потому что это конфигурация мониторинга.

Есть ещё четыре сценария: нехватка места на диске, отказ PostgreSQL, отказ Nginx и потери сетевых пакетов. Они тоже демонстрационные.

## Как работает классификация

### Основной алгоритм `context_guarded`

1. **ML:** локальная SVM, обученная на текстах опубликованных Prometheus-правил, независимо предсказывает `category` и `severity` из названия и аннотаций события.
2. **Сверка источника:** если Prometheus передал допустимые `labels.category` и/или `labels.severity`, эти значения становятся рабочим решением для соответствующих полей. При отсутствии допустимой метки берётся ML-прогноз.
3. **Объяснение:** при разногласии источник и ML явно разделяются; инженер сверяет исходные метрики и правила. Оценка SVM **не выдается за статистически откалиброванную вероятность**; ручная проверка обязательна.
4. **Приоритет:** вычисляется по бизнес-политике (см. ниже) из рабочей критичности и окружения. Это **не третье независимо обученное предсказание**.

| Критичность | Production | Non-production |
| --- | --- | --- |
| `critical` | P1 | P2 |
| `warning` | P2 | P3 |
| `info` | P4 | P4 |

Если окружение отсутствует или неоднозначно, система консервативно применяет production-политику и требует проверки инженером.

### Дополнительные режимы

Переключаются через `CLASSIFIER_ENGINE` в `.env` (для новых анализов):

| Значение | Режим |
| --- | --- |
| `context_guarded` | **По умолчанию в v1.8:** ML + сверка с метками Prometheus |
| `context` | Самостоятельный прогноз SVM по названию и аннотациям |
| `learned` | Экспериментальная SVM, обученная только на названиях |
| `ml` | Экспериментальный гибрид правил и SVM |
| `v2` | Расширенный офлайн-классификатор на экспертных правилах |
| `legacy` | Исходный классификатор версии v1.1 |

Сравнение в карточке — **read-only GET** `/api/v1/incidents/{incident_id}/analysis/compare`. Оно не изменяет анализ инцидента, регламент или историю. Совпадение двух прогнозов само по себе **не является метрикой точности**.

### Поиск регламентов

По умолчанию `EMBEDDING_BACKEND=hash`: векторные хеш-признаки + лексическое ранжирование, хранение в `pgvector`. Это **не нейросетевая семантика**. Необязательная локальная модель `intfloat/multilingual-e5-small` доступна как отдельный эксперимент (`INSTALL_E5=1` и настройка `EMBEDDING_BACKEND`). Для перехода между hash и E5 необходимо пересчитать векторы регламентов; подробности в [инструкции E5](docs/EXPERIMENTAL_E5.md).

## Проверка качества ML

Для обучения использованы **опубликованные конфигурации Prometheus**, а не логи реальных промышленных аварий. Собрано 745 определений предупреждений с источниками, названиями, аннотациями и метками; категория размечена по семейству экспортёра. Разделение по семействам сделано для снижения утечек между выборками.

| Выборка | Примеров | Применение |
| --- | ---: | --- |
| Обучение | 553 | Обучение |
| Валидация | 74 | Выбор параметров |
| Отложенная проверка | 118 | Сравнение на других семействах экспортёров |

Для **самостоятельной ML-модели по названию и аннотациям** на отложенной выборке получено:

| Метрика | Результат |
| --- | ---: |
| Категория | **67,8%** |
| Критичность | **80,5%** |
| Совместное совпадение категории и критичности | **55,1% (65/118)** |

**Требование 90% независимой точности на реальных инцидентах не доказано.** Отложенная выборка содержит мало сетевых предупреждений; результаты не являются промышленной гарантией. Отдельный тест передачи `severity` от Prometheus проверяет правильность обработки **готовой метки источника**, а не точность её предсказания.

Подробности: [ML Engineering Report](docs/ML_ENGINEERING_V16_REPORT.md), [разногласия ML и Prometheus в v1.8](docs/SOURCE_GUARD_V18.md), [сравнение моделей в UI](docs/ML_COMPARISON_V17.md).

GitHub Actions запускает тесты Python, обучение ML, оценочные скрипты, проверки фронтенда и сохраняет JSON-артефакт `sentinel-ai-ml-evaluation` с матрицами ошибок. При этом **полный Docker Smoke Test после изменений v1.8 в GitHub Actions не выполняется автоматически**; для защиты требуется проверка на машине команды.

## Архитектура

| Компонент | Стек |
| --- | --- |
| Frontend | React, TypeScript, Vite, Nginx |
| Backend | Python 3.12, FastAPI, SQLAlchemy, scikit-learn |
| Фоновые задачи | Celery, Celery Beat, Redis |
| Хранилище | PostgreSQL 16 + pgvector |
| Мониторинг | Prometheus, отдельный демонстрационный exporter |
| Развёртывание | Docker Compose: `db`, `redis`, `exporter`, `prometheus`, `api`, `worker`, `scheduler`, `frontend` |

**Поток данных:** Prometheus → фоновая синхронизация → PostgreSQL → ML + проверка меток источника → поиск регламентов → API → оператор. Создаются демо-пользователи и базовые регламенты; данные и история хранятся в Docker-томах.

Основные каталоги: `backend/` (API, ML, фоновые задачи, тесты), `frontend/`, `prometheus/`, `exporter/`, `scripts/`, `docs/` и `contracts/`.

## Ограничения и безопасность

Sentinel AI v1.8 — **демонстрационный MVP**, не самостоятельная промышленная система восстановления. Интегрирован Prometheus; Zabbix и платные внешние LLM не подключены. Решения об инфраструктуре принимает инженер; фразы «модель 90% точна» и «CPU действительно достиг 95%» не подтверждаются демонстрационными данными.

Демо-пароли и секреты обязательно заменять вне локального окружения. Не загружать недоверенные файлы `joblib` / `pickle` — при десериализации они могут выполнять код. Для промышленного внедрения нужны HTTPS, миграции БД, нормализация источников, независимая экспертная оценка классификации и эксплуатационное тестирование.

Остановка без удаления данных: `docker compose down`. **Не добавляй `-v`**, если нужно сохранить историю.
