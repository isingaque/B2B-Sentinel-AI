# Sentinel AI

**Система поддержки дежурного инженера при обработке инфраструктурных инцидентов**

**Версия:** 1.1 (MVP)  
**Проект:** кейс № 8 хакатона ТПУ «ИИ-Ассистент Дежурного»  
**Статус проверок:** [GitHub Actions](https://github.com/isingaque/B2B-Sentinel-AI/actions)

Sentinel AI получает предупреждения из Prometheus, регистрирует и классифицирует инциденты, подбирает регламенты реагирования и предоставляет оператору последовательный чек-лист. Все действия на инфраструктуре выполняются человеком: система не запускает команды, не перезапускает сервисы и не изменяет конфигурации серверов автоматически.

## Задача и решение

При большом количестве уведомлений мониторинга дежурному инженеру необходимо быстро определить характер неисправности, её критичность и порядок действий. Разрозненные инструкции и ручной учёт затрудняют реагирование и последующий аудит.

Sentinel AI объединяет получение событий, первичную классификацию, поиск подходящих регламентов и фиксацию действий инженера в едином интерфейсе.

| Направление | Реализация |
| --- | --- |

| Подбор регламентов | Ранжирование инструкций с использованием pgvector, векторного и лексического сходства |
| База знаний | Создание, редактирование, версионирование, CSV-импорт, архивирование и восстановление регламентов |
| Контроль действий | Подтверждение шагов оператором, обязательные пояснения для пропущенных шагов, журнал событий |
| Интерфейс | Дашборд, список и карточки инцидентов, фильтры, история действий и управление регламентами |

## Быстрый запуск

**Требования:** Docker Engine или Docker Desktop с Docker Compose v2; доступ в интернет для первой сборки; свободные порты 8080 и 9090. Установка Python или Node.js на хост не требуется.

**Windows PowerShell:**

```powershell
git clone https://github.com/isingaque/B2B-Sentinel-AI.git
cd B2B-Sentinel-AI
Copy-Item .env.example .env
docker compose up --build -d
```

**Linux / macOS:**

```bash
git clone https://github.com/isingaque/B2B-Sentinel-AI.git
cd B2B-Sentinel-AI
cp .env.example .env
docker compose up --build -d
```

После запуска:

| Сервис | Адрес |
| --- | --- |
| Веб-интерфейс | http://localhost:8080 |
| Swagger / API | http://localhost:8080/docs |
| Prometheus | http://localhost:9090 |

Демонстрационные учётные записи: `admin` и `operator`. Пароль по умолчанию для обеих — `DemoPass123!`. Значения задаются через `.env` и **предназначены только для локального тестирования**.

Проверка контейнеров и состояния Backend:

```bash
docker compose ps
```

```bash
curl http://localhost:8080/health/ready
```

## Демонстрационный сценарий

1. Войти в интерфейс под `admin` и открыть раздел «Симулятор».
2. Включить сценарий «Высокая загрузка CPU». Симулятор устанавливает тестовую метрику в exporter; Prometheus формирует предупреждение. **Реальная нагрузка на процессор не создаётся.**
3. Открыть раздел «Инциденты» после нескольких циклов опроса. Проверить категорию, критичность, приоритет и предложенный регламент.
4. Взять инцидент в работу, принять план реагирования и вручную подтвердить или пропустить шаги с указанием причины.
5. Сбросить сигналы в симуляторе. После перехода предупреждения в состояние `resolved` завершить обработку инцидента.
6. Проверить запись о закрытии и журнал действий. Дополнительно можно продемонстрировать редактирование, архивирование и восстановление регламентов.

Доступные сценарии: высокая загрузка CPU, нехватка места на диске, недоступность PostgreSQL, отказ Nginx и потери сетевых пакетов.

## Архитектура и технологии

| Компонент | Технологии и назначение |
| --- | --- |
| Frontend | React, TypeScript, Vite, Nginx |
| Backend | Python, FastAPI, SQLAlchemy |
| Фоновая обработка | Celery, Celery Beat, Redis |
| Хранение | PostgreSQL 16, pgvector |
| Мониторинг | Prometheus, собственный демонстрационный exporter |
| Инфраструктура | Docker Compose, восемь сервисов |

Поток данных: **Prometheus → фоновая синхронизация → PostgreSQL → классификация и поиск регламентов → REST API → интерфейс оператора**.

Backend управляет авторизацией и жизненным циклом инцидентов. Celery обрабатывает синхронизацию и анализ в фоновом режиме. PostgreSQL хранит инциденты, регламенты, результаты анализа и аудит. Оператор подтверждает действия в интерфейсе; команды инфраструктурным системам не отправляются.

При первом запуске создаются демонстрационные пользователи, источник мониторинга и пять базовых регламентов. Созданные пользователем записи сохраняются в локальном Docker-томе PostgreSQL, а не в Git-репозитории.

## Реализация AI и ограничения

В стабильной конфигурации v1.1 применяется **локальный классификатор на экспертных правилах**, а не внешняя большая языковая модель. Классификатор учитывает содержание события и, если источник передал `category` или `severity`, использует эти метки. Поэтому значение уверенности, отображаемое для отдельного события, не следует интерпретировать как измеренную точность на независимых данных.

Поиск регламентов по умолчанию использует хешированные символьные признаки размерности 384 и сравнение сходства с дополнительной лексической оценкой. Это векторный поиск, но **не нейросетевая семантическая модель**.

Экспериментальная поддержка `multilingual-e5-small` предусмотрена отдельно и **не включена по умолчанию**. Интеграция с LLM через API вынесена в следующий этап разработки. Описание и ограничения: [оценка классификатора](docs/AI_EVALUATION.md), [экспериментальный E5](docs/EXPERIMENTAL_E5.md).

## Проверка работоспособности

Автоматический процесс [GitHub Actions](https://github.com/isingaque/B2B-Sentinel-AI/actions) выполняет тесты Backend и сборку Frontend. Сквозной Smoke Test дополнительно был успешно выполнен на локальном Docker-окружении.

**Оценка классификатора без заранее заданных меток Prometheus:**

| Набор | Событий | Точная категория и критичность одновременно |
| --- | ---: | ---: |
| Исходный синтетический | 24 | 22 из 24 — 91,7% |
| Дополнительный синтетический | 48 | 46 из 48 — 95,8% |

Оба набора составлены вручную для тестирования. Эти результаты **не доказывают точность не ниже 90% на реальных промышленных инцидентах**. Для такой оценки необходим независимо размеченный набор производственных событий.

**Воспроизведение оценки и сквозного теста** из корня проекта в PowerShell после запуска контейнеров:

```powershell
docker compose cp .\backend\tests api:/srv/tests
docker compose cp .\scripts\evaluate_ai.py api:/srv/evaluate_ai.py
docker compose exec api python /srv/evaluate_ai.py

docker compose cp .\scripts\smoke_test.py api:/tmp/smoke_test.py
docker compose exec -e DUTY_URL=http://localhost:8000 api python /tmp/smoke_test.py
```

Smoke Test изменяет демонстрационные данные и предназначен для тестового окружения. Успешный сквозной запуск завершается строкой `SMOKE TEST PASSED`.

## Границы применения

Sentinel AI v1.1 — демонстрационный MVP, а не готовая система промышленного автоматического восстановления. В текущем релизе реализована интеграция с Prometheus; Zabbix и внешняя LLM через API не подключены. Для производственного использования дополнительно необходимы настройка безопасности и секретов, HTTPS, надёжные процедуры миграции БД и проверка классификации на реальных данных.

Для остановки без удаления данных используйте `docker compose down`. Не применяйте удаление Docker-томов к окружению с нужной историей инцидентов.
