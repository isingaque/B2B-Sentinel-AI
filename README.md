# Sentinel AI v1.8

**ИИ-ассистент дежурного инженера** · кейс № 8 хакатона ТПУ

Sentinel AI принимает предупреждения из **Prometheus**, регистрирует инциденты, определяет категорию, критичность и приоритет, предлагает регламенты и помогает дежурному инженеру вести чек-лист и аудит действий.

В основной версии используется **локальная обученная модель TF-IDF + Linear SVM** совместно с проверкой меток мониторинга. Система консультирует, но **не исполняет команды на серверах автоматически**.

## Запуск одной командой

Требования: запущенный **Docker Desktop** (Windows) либо Docker Engine с **Docker Compose v2** (Linux/macOS) и доступ в интернет для первой сборки образов. Python, Node.js, регистрация у AI-провайдеров и API-ключи **не нужны**.

Скачайте или клонируйте репозиторий и откройте терминал **в папке с `docker-compose.yml`**. Выполните одну команду:

```bash
docker compose up --build -d
```

**Готово:** Docker Compose собирает и поднимает восемь сервисов, устанавливает зависимости, обучает локальные ML-модели внутри Docker-образа, создаёт базу данных и запускает веб-интерфейс.

Создавать `.env` **не требуется**: для локального демо все параметры, включая режим `CLASSIFIER_ENGINE=context_guarded`, уже имеют значения по умолчанию в `docker-compose.yml`. Первая сборка может быть длительной, поскольку устанавливается `scikit-learn` и выполняется обучение.

| Сервис | Адрес |
| --- | --- |
| **Приложение Sentinel AI** | **http://localhost:8080** |
| REST API / Swagger | http://localhost:8080/docs |
| Prometheus | http://localhost:9090 |
| Состояние Backend | http://localhost:8080/health/ready |

**Демо-вход:** `admin` / `DemoPass123!` (также доступна учётная запись `operator` с тем же демо-паролем).

Для проверки работы контейнеров: `docker compose ps`. Для безопасной остановки: `docker compose down`. **Не используйте `down -v`** — это удаляет Docker-тома с сохранёнными данными.

> **Порты менять не нужно:** стандартный запуск использует **8080** и **9090**. Если они уже заняты другой запущенной копией проекта, сначала остановите ту копию через Docker Desktop или её `docker compose down`. Не запускайте разные версии одновременно на тех же портах.

Для изменения паролей, портов или режима анализа при необходимости: `Copy-Item .env.example .env` (PowerShell) либо `cp .env.example .env` (Linux/macOS), затем отредактируйте `.env`. Для публичного размещения обязательно замените все демо-пароли и секреты, настройте HTTPS и управление доступом.

## Что реализовано

| Функция | Возможности |
| --- | --- |
| Получение инцидентов | Периодический опрос Prometheus HTTP API, дедупликация, обновление состояния и история |

| **Сверка с Prometheus** | Если источник передал корректные `category` или `severity`, рабочее решение использует их; при расхождении с прогнозом ML требуется проверка инженером |

| Сравнение алгоритмов | В карточке можно сопоставить экспертные правила и ML на **одинаковом тексте без готовых меток ответа** |
| Подбор регламентов | Векторное и текстовое сходство, PostgreSQL + pgvector; слабые совпадения выделены |
| База знаний | CRUD, CSV-импорт, версии регламентов, архивирование и восстановление |
| Работа дежурного | Принятие плана, ручные чек-листы, подтверждение шагов, комментарии, аудит |
| Администрирование | Роли, JWT, интерфейс аналитики, симулятор пяти инцидентов |

### Как выглядит основная ML-логика

Основной режим: `CLASSIFIER_ENGINE=context_guarded`.

1. Локальная SVM независимо оценивает **категорию** и **критичность** по тексту события.
2. Если Prometheus предоставил допустимые метки `category` и `severity`, эти сведения источника используются в **рабочем решении**; при отсутствии меток остаётся прогноз модели.
3. Противоречия явно отмечаются. Финальное решение по реагированию принимает инженер.
4. Приоритет определяется по единой бизнес-политике, а не отдельным ML-предсказанием:

| Критичность | Production | Non-production |
| --- | --- | --- |
| `critical` | P1 | P2 |
| `warning` | P2 | P3 |
| `info` | P4 | P4 |

При отсутствии надёжной метки окружения система консервативно использует политику production и требует ручной проверки.

**Важно:** метка `severity=critical`, установленная самим Prometheus, — это информация мониторинга, **не показатель точности ML**. SVM не выдаёт достоверную вероятность без отдельной калибровки; система не показывает выдуманные проценты уверенности в её предсказании.

По умолчанию для поиска регламентов используется `EMBEDDING_BACKEND=hash` (векторное хеширование и лексическое сравнение). Отдельная локальная модель эмбеддингов E5 доступна как **необязательный эксперимент**: [документация](docs/EXPERIMENTAL_E5.md).

## Демонстрация для жюри

1. Откройте **http://localhost:8080**, войдите под `admin`, перейдите в **«Симулятор»**.
2. Включите сценарий **«Высокая загрузка CPU»** и покажите возникшее предупреждение в **Prometheus → Alerts**.
3. Откройте инцидент в Sentinel AI. Покажите классификацию, критичность, приоритет и объяснение.
4. Нажмите **«Сравнить правила и ML»**: два классификатора получат одинаковый текст, а панель дополнительно покажет метки Prometheus и выбранное рабочее решение. В CPU-сценарии источник задаёт `critical`; SVM может выдать `warning`.
5. Покажите предложенный регламент, принятие плана и ручной чек-лист.
6. В симуляторе нажмите **«Сбросить все сигналы»**. После обновления Prometheus предупреждения станут неактивными, но названия правил останутся в интерфейсе — они описаны в конфигурации.

Другие сценарии: заполнение диска, недоступность PostgreSQL и Nginx, потери сетевых пакетов.

**Все пять сценариев симулируются:** включается метрика `demo_incident_active`. Например, демонстрационный CPU-сигнал **не означает, что реальная загрузка процессора достигла 95%**.

## Оценка ML и её ограничения

Для исследования использованы **745 опубликованных определений правил Prometheus**, а не журнал реальных аварий. Обученная модель по названию и аннотациям проверялась на правилах других семейств экспортёров:

| Выборка | Количество |
| --- | ---: |
| Обучение | 553 |
| Валидация | 74 |
| Отложенная проверка | 118 |

| Метрика на отложенных 118 правилах | Результат |
| --- | ---: |
| Категория | 67,8% |
| Критичность | 80,5% |
| **Оба признака одновременно** | **55,1% (65/118)** |

Это воспроизводимые результаты исследования, **не доказательство 90% точности на реальных независимых инцидентах**. Метка критичности Prometheus в рабочем режиме не является самостоятельно предсказанным результатом.

Подробные отчёты: [ML Engineering](docs/ML_ENGINEERING_V16_REPORT.md), [сверка ML с Prometheus](docs/SOURCE_GUARD_V18.md), [сравнение классификаторов](docs/ML_COMPARISON_V17.md).

## Архитектура и проверка

**Стек:** React + TypeScript + Vite + Nginx; FastAPI + SQLAlchemy + scikit-learn; PostgreSQL 16 + pgvector; Redis + Celery + Celery Beat; Prometheus; Docker Compose.

**Путь данных:** Prometheus → фоновая синхронизация → PostgreSQL → ML и сверка с метками → подбор регламентов → API → веб-интерфейс → ручные действия инженера.

Восемь сервисов Compose: `db`, `redis`, `exporter`, `prometheus`, `api`, `worker`, `scheduler`, `frontend`.

[GitHub Actions](https://github.com/isingaque/B2B-Sentinel-AI/actions) проверяет Backend, сборку Frontend и публикует результаты оценки ML. Проверки на синтетических сценариях не заменяют испытания на промышленных данных.

**Sentinel AI v1.8 — демонстрационный MVP.** Zabbix, платные LLM API и самостоятельное выполнение инфраструктурных команд не реализованы. Для промышленного применения нужны HTTPS, защита секретов, управление миграциями, реальные размеченные инциденты и эксплуатационные испытания.
